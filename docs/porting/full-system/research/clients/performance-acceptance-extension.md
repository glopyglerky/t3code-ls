# Whole-product performance acceptance extension

Status: proposed acceptance design, not benchmark results. Baseline is `pingdotgg/t3code@28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f`.

This adds journeys 34–60 to the prior 1–33 database, lifecycle, cloud and offline matrix at `../database/nonserver/performance-acceptance-matrix.md`. The expanded user goal includes all T3-owned clients, not only their server database. The 30 capability IDs below refer to `capability-map.md`, whose entries carry immutable source citations.

## Comparison rules

Compare shipped stock and candidate implementations that produce the same user outcome with the same supported capability set. Pin versions, fixture content, result ordering/limits, account/provider behavior, hardware, display/refresh rate, OS, network, process topology, concurrency and durability. Use native hardware and real platform input for final interaction acceptance; browser emulation cannot establish native keyboard, IME, accessibility, widget, permission or background parity.

Keep cold process, cold filesystem/cache, warm application, cached offline, refreshed authoritative and steady-state sustained workloads separate. Include giant individual messages/files and many small objects, not just a row count. Record cancellation and stale-result work. Long benchmarks must include compaction, cache eviction, uploads and background updates.

For interactive paths report p50/p95/p99 input-to-paint or requested-outcome latency, longest stall, frame-time distributions, CPU and energy, peak/retained memory, protocol bytes and cross-process/native bridge transfers. For operations report start-to-durable acceptance, first useful result and final completion separately. Do not claim a network/IdP/provider wait as local database or rendering cost.

Use the current upstream optimizations described in `client-platform-review.md` as the baseline. Historical commit ratios demonstrate successful techniques; they do not set current end-to-end measurements. Establish concrete absolute budgets from measured stock and expected interaction requirements. This research deliberately does not invent millisecond targets.

## Promotion rules for a complete Rust product

A toolkit demo or one favorable storage benchmark cannot close a capability family. Each platform must preserve the observable outcome and lifecycle of the applicable family, including errors, offline states, permissions, cancellation and cleanup.

Acceptance requires a meaningful improvement in the intended dominant journeys, no material regression in other required interactions, bounded steady-state resources and successful recovery. Keep per-journey results visible. Set thresholds and weighting before collecting candidate results.

Retain existing clients until their replacements pass the agreed native scope. Route or feature removal does not count as a performance improvement. External provider-owned formats stay compatible. Native client migration must import owned caches/settings/drafts/outbox/credential references safely and respect which data is disposable.

The remaining dedicated audits are Android native rendering/input, all accessibility combinations, media/codecs, SnapShot, device streaming, store/update compatibility and complete route-state coverage. This is a full-product acceptance framework, not a claim that those audits or implementation tests have run.
