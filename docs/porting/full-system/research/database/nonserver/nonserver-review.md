# T3 Code persistence outside the main server store, and lifecycle requirements

## Scope and confidence

Upstream repository: `pingdotgg/t3code`. All source facts below refer to commit **28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f**, tree `af9112ce82be93109079ca7b7a89f7182455eca5`. Source was inspected with immutable git reads from an existing checkout; its working HEAD was not used. No running user database was opened, and no checkout, application, deployment, benchmark or test was changed or run.

This work inventories non-server owners and reviews selected implementations plus server operational lifecycle. Main server table/query completeness belongs to the separate server review. The research captured 78 source files: 28 files read in full, 34 inspected at selected sections/call sites, and 16 retrieved for navigation but not semantically reviewed. Two guessed paths were absent and are recorded rather than treated as evidence. See [coverage.json](coverage.json) for every path, blob SHA, pinned source URL and classification. Raw source copies are omitted from this publication.

The owner discovery searches found 113 product-path database-reference files and 42 client file-storage-reference files. These are discovery counts, **not 113 databases**. There are false positives, integration files and generated schemas. A broad lifecycle grep also matched ordinary TypeScript imports and is only a navigation aid. Vendored `.repos/alchemy-effect` examples were excluded from product ownership. The task-cache vendor is different: its runtime code and migrations are imported by the production cache and therefore are in scope.

## Decision-relevant result

T3 Code does not have one interchangeable database. The local authoritative server store is one candidate for a Rust implementation. Client caches, secrets, unsent messages, provider session stores, remote relay coordination and task-cache policy each have separate ownership and failure semantics. A faster main server database does not by itself speed those paths.

A one-authority native server design remains feasible. It needs typed application services and query-shaped reads, transactional event/projection/receipt/outbox/index updates, and explicit lifecycle machinery. It should preserve the host and external-format boundaries below. This review does not establish that Fjall, redb or another Rust engine is faster for those services; no engine comparison was executed.

### Mobile semantics

The SQLite cache uses a composite primary key and `WITHOUT ROWID`, with an environment/update-time index. Pull-request cache retention is at most 256 entries, 32 MiB and 30 days per environment; a payload over 4 MiB is rejected. Its SQL pruning uses row-number and cumulative byte windows. The source invokes save then prune sequentially; this review does not claim the pair is one explicit transaction.

Mobile preferences differ from caches. When SQLite cannot save, the code writes a timestamped SecureStore fallback. On load it chooses the newer valid fallback, replays it when SQLite is available, and removes stale fallback/legacy values only in the corresponding successful paths. Updates have a semaphore and monotonic timestamp. Replacing this with a cache-like best-effort write would lose a user-visible recovery guarantee. [apps/mobile/src/persistence/mobile-preferences.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/mobile/src/persistence/mobile-preferences.ts)

The catalog uses SecureStore, not the mobile SQLite database. One in-memory semaphore serializes read-transform-write; cached state updates after persistence. Corrupt catalogs have defined deletion/legacy fallback behavior. Outbox files are independently reloadable; per-item read errors do not necessarily discard the whole queue. Draft cleanup checks draft, outbox and incoming-share references before deleting attachment files or releasing pending uploads. [apps/mobile/src/connection/catalog-store.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/mobile/src/connection/catalog-store.ts), [apps/mobile/src/state/thread-outbox-storage.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/mobile/src/state/thread-outbox-storage.ts), [apps/mobile/src/state/use-composer-drafts.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/mobile/src/state/use-composer-drafts.ts)

### Browser semantics and demonstrated design choices

The connection store caches one IDB handle and forgets/reopens it after close/version-change failures. Writes complete on transaction completion. Thread cache writes use latest-write ordering; an oversized new thread snapshot removes its old persisted copy so stale history cannot reappear after restart. Browser-only catalog recovery can quarantine corrupt serialized data; desktop catalog requests use its native bridge instead.

PR query pruning amortizes index walks: a batch counter is stored in the same database, shared by tabs, and the index walks after 32 saves or 1 MiB of writes, keeping headroom under the same 256-row/32-MiB caps. This is a concrete upstream optimization pattern: reduce work performed per logical update while retaining bounds. It is not an engine speed measurement. [apps/web/src/connection/storage.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/web/src/connection/storage.ts)

Composer writes are deferred 300 ms; serialization merges only changes made by the current tab over fresher stored state. Before-unload flush is explicit. Preview browser history has its own IDB record, per-project URL caps, a BroadcastChannel, and a localStorage fallback/migration source retained until the IDB snapshot commits. Old-version tabs can still contribute visits, so migration is re-merged rather than assumed one-time forever. PR routing grants deliberately retain separate localStorage keys to prevent stale unrelated catalog writes from restoring revoked trust. [apps/web/src/composerDraftStore.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/web/src/composerDraftStore.ts), [apps/web/src/browserHistoryStore.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/web/src/browserHistoryStore.ts), [apps/web/src/connection/storage.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/web/src/connection/storage.ts)

Other discovered client persistence consumers include prompt stash, closed views, terminal/diff/right-panel/UI state, issue/PR list preferences, voice consent, managed relay tokens, mobile cloud proof keys, permission notices and voice grants. Those are classified as filename-level inventory unless their implementation is separately listed as reviewed. No product OPFS persistence implementation or PrismaClient use appeared in the explicit searches; the relay source positively establishes PostgreSQL/Drizzle. No direct `state.vscdb` reader appeared in these searches; do not substitute that filename for the actual Cursor SDK store.

## External SQLite and provider compatibility

OpenCode usage selects row IDs and change markers before loading bodies, reuses unchanged records, and fetches **64 misses per page**. SQL projects only token/cost/model/provider/time/ID fields from potentially huge JSON message bodies. Filtering runs in SQLite, a read transaction provides a coherent view, and a reader worker keeps the scan off the server event loop. Legacy table shapes and fork lineage are handled. The use of `octet_length(data)` avoids materializing bodies just to test length. These are concrete mechanisms behind the upstream improvement the parent review investigates; this file alone does not prove a numerical speedup. [packages/provider-opencode/src/server/usage.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/packages/provider-opencode/src/server/usage.ts)

OpenCode credential lookup reads the selected active credential with a small busy timeout; remote externally configured OpenCode servers do not borrow the host's account. A replacement should not rewrite these provider tables or add indexes to their databases as an incidental optimization. [packages/provider-opencode/src/server/usageLimits.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/packages/provider-opencode/src/server/usageLimits.ts)

## Lifecycle requirements a main-store rewrite must implement

### Ownership and command access

The current owner lock is an exclusive transaction on a file that must not be unlinked; OS process exit releases it even after SIGKILL. Desktop, server, service launcher and SSH all understand this protocol. The service also has launcher/serving locks. A native owner RPC plus offline exclusive lease is a coherent proposed design, but merely substituting a different lock for the server alone leaves older launchers blind to it. Keep transitional compatibility or coordinate the launcher protocol upgrade, canonical path handling, lock-file replacement protection, handover and recovery. [apps/server/src/serverOwnership.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/server/src/serverOwnership.ts), [apps/desktop/src/backend/DesktopHomeOwner.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/desktop/src/backend/DesktopHomeOwner.ts), [apps/server/src/serviceLauncher.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/server/src/serviceLauncher.ts), [packages/ssh/src/tunnel.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/packages/ssh/src/tunnel.ts)

### Import and schema evolution

First V2 launch copies legacy `state.sqlite` into a compacted incremental-vacuum snapshot on a worker, then publishes the complete snapshot with a no-replace link. The original remains unchanged. Abandoned temporary copies are cleaned only when their creating process is no longer alive. Legacy transcripts import lazily. Existing migrations run one transaction per migration, enabling restart after the last completed migration, and check ID/name collisions that would skip required V2 schema. A Rust migration needs a versioned, resumable source-to-native transformation with source retained and final publication only after consistent completion. [apps/server/src/persistence/initializeV2Database.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/server/src/persistence/initializeV2Database.ts), [apps/server/src/persistence/Migrations.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/server/src/persistence/Migrations.ts)

### Update trial, backup and rollback

Service updates already implement more than copying a database file. Backup uses a per-update staging directory, file fsync, atomic publish and directory fsync. Where clone is unavailable, an online path pins a SQLite read transaction while copying main data, then copies WAL after the server stops; it intentionally omits SHM. A resumed trial reuses its original backup rather than overwriting it with already-migrated data. Restore writes and fsyncs `.restore-pending` before modifying live files, follows symlink targets, and prevents starting a partial restore after a crash. Disk-space and clone-aware checks precede updates. Native checkpoints must replace this protocol with a coherent generation and manifest, including every log/index/blob file needed to reopen that generation, and maintain trial/commit/rollback state transitions. [apps/server/src/serviceLauncher.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/server/src/serviceLauncher.ts)

A preserved pre-migration SQLite copy supports recovery to that point; it does **not** make later native writes visible to an older SQLite build. Decide whether rollback means failed trial rollback before admission of normal work, or post-commit downgrade carrying subsequent writes. The latter requires a proven export/compatibility path; no blanket transparent-downgrade promise follows from retaining the old file.

### Space reclamation, doctor and historical facts

Background event compaction persists a completion timestamp so restart does not trigger another large no-op scan. It runs six-hourly, starts after a delay, and uses a 10% maintenance duty cycle with approximately 25-ms work slices. Incremental reclamation yields between pages and bounds work to 1,024 pages per pass. Manual reclaim stops the service, locks the home/database, prunes superseded events, vacuums, rebuilds search and truncates WAL. It inspects free disk space and refuses unsafe legacy removal if live legacy records are absent from current projections. A native LSM needs equivalent admission/latency controls for compaction, retention and index rebuild, plus usable progress/errors and disk-space estimation; moving work to a background thread does not eliminate IO contention. [apps/server/src/persistence/DatabaseStorage.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/server/src/persistence/DatabaseStorage.ts), [apps/server/src/persistence/DatabaseMaintenance.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/server/src/persistence/DatabaseMaintenance.ts), [apps/server/src/cli/doctor.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/server/src/cli/doctor.ts)

One easily missed historical dependency: Codex usage tier recovery reads T3-owned run-attempt/provider-turn projections and the **first** matching `run.updated` running event. Later steering must not overwrite that original fact, and ambiguous duplicates are not guessed. A different retention policy must retain or materialize it. [apps/server/src/usage/CodexUsageHistory.ts](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/server/src/usage/CodexUsageHistory.ts)

### User recovery and developer tools

Upstream documents no whole-thread export command. User recovery is stopping the server and copying `userdata`, keeping legacy database copies unchanged. Settings, attachments and workspace files are not replaced by a transcript-only database export. The isolated `t3-sqlite-state` developer tool supports read-only queries; writes reject the shared home, make a permission-restricted backup first, then execute in a transaction. A native plan should provide equivalently scoped inspection/seeding and a documented backup/restore workflow. Export is a proposed feature, not something assumed to exist today. ## Implications for the proposed Fjall authority

The proposed single transactional authority is reasonable as an architecture candidate, provided its transaction covers event append, command receipt, projections, outbox and every correctness-sensitive index at one visible sequence. LSM engine selection alone does not implement those semantics.

Before calling the owner set complete, map all server repositories/services into it: auth sessions/pairing/connect devices, provider session runtime, scheduled tasks, PR review guides/viewed files, peer links, known workspaces, settings, attachment lifecycle and historical usage. These names appear in the owner inventory; the separate server review must establish their exact transactions and durability. They cannot disappear inside an unspecified “projected records” bucket.

Use stable versioned codecs and explicit key ordering. Encode time/rank/sequence so scans serve the exact API ordering; ensure projection/index rebuild is generation-safe and does not reveal partly rebuilt state. Offload large read/decode work without unbounded copying back into the runtime. Keep external provider SQLite and Cursor SDK stores separate. Keep browser/mobile host storage, relay PostgreSQL/DO and task-cache D1/R2 as distinct implementations of their own contracts.

No new benchmark was run. A complete acceptance matrix is in `performance-acceptance-matrix.md`. The current five-operation server persistence fixture says nothing about most owner rows above; it cannot establish whole-product performance.
