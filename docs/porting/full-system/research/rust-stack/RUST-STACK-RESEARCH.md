# Rust application stack for a faithful T3 Code reimplementation

Research date: 2026-11-22. Product comparison target: `pingdotgg/t3code@28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f`. This report covers UI, terminal, Git, file watching/search and text/rendering. Database and networking research are separate. No implementation or performance run was performed.

## Decision

**Use one shared Rust application core, with purpose-built platform presentation layers: GPUI as the native desktop performance candidate, Makepad as the first native-mobile candidate and desktop challenger, and Dioxus compiled to WebAssembly with semantic DOM for the browser.** Use the selected toolkit's existing platform integrations and build the remaining Rust-owned adapters. Share domain state, commands, selectors, text parsing, diffing, indexing and terminal state; do not force every platform through one renderer merely to share view code.

Dioxus WebView on desktop and mobile is the sensible broad-coverage comparison implementation. It replaces first-party JavaScript application logic with Rust, but it retains the host browser engine, DOM, layout, GPU pipeline and generated JavaScript bridge. It is not equivalent to the native desktop performance architecture. It should not be assumed faster than upstream mobile's existing native composer, diff and terminal modules. Its usefulness is lowering the cost of delivering the Rust application and serving as a platform-coverage control.

This is an engineering recommendation, not a measured winner. No reviewed source proves that GPUI, Dioxus, Alacritty or a particular Rust dependency beats this pinned T3 workload. Native desktop removes some general-purpose rendering/GC boundaries; the shared core can eliminate repeated text work and conversions. Whether these opportunities outweigh new layout, FFI, synchronization and browser/WASM costs must be measured end to end.

The strict destination is all first-party feature logic in Rust. **Handwritten Swift/Kotlin/Java/TypeScript left in shipping product behavior is unfinished port scope.** Generated ABI glue may be an implementation technique, but cannot hide remaining feature logic. External OS frameworks, browser hosts and provider/Git executables must be listed separately from owned application code. A Rust application depending on Skia, Tree-sitter, system WebKit or a third-party provider is not a pure-Rust dependency tree.

### Recommended organization

| Layer | Concrete choice | Responsibility and reason |
|---|---|---|
| Shared application core | Rust crates with no GUI dependency | Domain reducers, state transitions, selected view models, session/device state, capability checks, orchestration contracts and settings schemas. One implementation across server/native/WASM where host capabilities permit. |
| Native desktop | GPUI plus AccessKit; platform browser view only where actual web content is required | Direct native rendering of chat/history, source/diff panes, palettes and terminal. The desktop UI should own only presentation and local interaction state. GPUI is pre-1.0; pin revisions and keep application models independent of its entity types. |
| Browser | Dioxus Rust/WASM semantic DOM | Preserve browser navigation, focus, selection, forms, accessibility, CSP and browser-native affordances. Render-heavy terminal remains a specialized surface, with a DOM accessibility/input layer. Rust/WASM workers can process text off the main thread. |
| Mobile | Makepad candidate with shared Rust state and render services; remaining Rust-owned platform adapters | Evaluate its actual IME/accessibility/WebView implementations first, then preserve the remaining app lifecycle, secure keys, speech, notifications, share extensions, widgets/live activities and preview policies. This is a porting workstream, not something a toolkit checkbox completes. |
| Terminal state | Qualify `alacritty_terminal` native/WASM as the Rust replacement candidate | One parser/grid implementation, separate host PTY and platform render/input adapters. Its WASM support is newly landed development code. Keep Ghostty behavior as the baseline oracle. |
| PTY | `portable-pty` on the host | Cross-platform spawn/read/write/resize/child lifecycle, from WezTerm. Use bounded blocking I/O workers where the API blocks. Browsers and ordinary mobile clients are viewers, not local PTY hosts. |
| Git | `gix` for demonstrated compatible operations; explicit Rust workflow completion for missing mutations | Persistent repository handles and typed object/status/diff access can avoid subprocess startup and reparsing. Current gix is not a complete Git replacement. External Git is a parity control or temporary dependency, not proof of completed Rust Git implementation. |
| Files/search | `notify` plus reconciliation, ripgrep library crates, optional `nucleo` for specified fuzzy ranking | Reuse well-tested engines; cache/reconcile repository state and bound work. Do not change T3 palette ranking semantics by substituting a fuzzy scorer. |
| Markdown/text/diff | Comrak or pulldown-cmark chosen by exact syntax parity; Ropey for large editable buffers; imara-diff for bounded line-first diffs | Parse once per source revision, cache stable blocks/spans, reuse results across views, compute intra-line diffs only in changed small regions. Preserve markdown semantics that can invalidate earlier output. |

## 1. Why these UI choices, and where they stop

Dioxus's pinned README and official 0.7 platform guide distinguish DOM/WASM web, native Rust code with WebView rendering on desktop, and the same WebView renderer on mobile. Its WGPU renderer is explicitly experimental. The current Blitz README calls the engine beta, suitable for early adopters willing to accept bugs and missing features, and says it is still being brought to production quality. Blitz is not a complete web engine: its purpose is HTML/CSS rendering, and it deliberately leaves many browser services to ordinary Rust crates. Arbitrary MCP HTML applications and website previews therefore require a real browser host; Blitz is not a demonstrated standards-compatible replacement for those surfaces.

Sources: [Dioxus pinned README](https://github.com/DioxusLabs/dioxus/blob/0a7242a2a72b08975584bf8ecb05076a5ee0b9c7/README.md), [platform guide](https://dioxuslabs.com/learn/0.7/guides/platforms/), [Blitz pinned README](https://github.com/DioxusLabs/blitz/blob/165d698c31d00b9614664dddfbb865ff030948b3/README.md).

GPUI has the strongest directly relevant production example in Zed: a native editor with large text, terminal, async state and interactive panes. Its source documents macOS, Windows, Linux and FreeBSD backends, a hybrid retained/immediate architecture, custom elements and AccessKit accessibility. That supports choosing it as the desktop performance candidate. It does not demonstrate that a T3 view is fast by default; expensive work still must leave the UI thread, list identities must remain stable, and custom controls must supply accessible roles/actions/text.

Current GPUI mobile forks exist, but their own release documentation explicitly says the dependency switch does not complete mobile IME composition, accessibility or lifecycle hooks. They are not a substitute for proving T3 mobile parity. GPUI's official source reviewed here does not establish a production browser/mobile stack equivalent to its desktop stack.

Sources: [GPUI pinned README](https://github.com/zed-industries/zed/blob/f126950f9d3b62666f97437ae5d4ccac2272c4db/crates/gpui/README.md), [GPUI accessibility guide](https://github.com/zed-industries/zed/blob/f126950f9d3b62666f97437ae5d4ccac2272c4db/crates/gpui/src/_accessibility.rs), [GPUI mobile fork release](https://docs.rs/crate/gpui-pre-mobile/0.1.0).

### Mobile completion blockers

AccessKit itself now has Android and iOS adapters. It is incorrect to repeat older claims that AccessKit is desktop-only. That does not guarantee every toolkit wires those adapters correctly, and it does not make a canvas app automatically equivalent to a semantic browser document.

The same pinned AccessKit README says released adapters do not yet support rich text or hypertext, and lists the web adapter as planned. A native T3 chat/code surface must therefore prove useful screen-reader navigation, content, links, selection and actions; saying that GPUI uses AccessKit does not discharge those obligations. GPUI's own crate is Apache-2.0, while Zed's application terminal crate is GPL-3.0-or-later; adopting GPUI does not imply that every Zed application module has the same license.

The Android activity abstraction has a concrete limitation. Its documentation says NativeActivity permits an application without Java/Kotlin, but has no built-in IME support adequate for production text input. GameActivity supports IME. It further states that subclassing Activity cannot be done from Rust/JNI alone, and moderately complex applications normally require an Activity subclass. Rust-generated Java adapters are a possible bridge; retaining handwritten Kotlin feature logic is unfinished under the user's strict goal. An ASCII-only demo is not an acceptable replacement for upstream's composer.

On iOS, objc2 exposes UIKit and UITextInput bindings. Apple's widgets and Live Activities use SwiftUI definitions in a WidgetKit extension. objc2's framework tracker identifies WidgetKit as Swift; it does not establish a ready Rust binding. A generated Swift view/ABI adapter or additional interoperability work is needed to meet strict all-first-party-Rust completion. The plan must preserve the feature while solving that bridge, not silently remove widgets or declare the remaining Swift accepted.

Sources: [AccessKit pinned README](https://github.com/AccessKit/accesskit/blob/0977e030f2c162d52ec844335a5ea454b2cb4326/README.md), [Android activity pinned README](https://github.com/rust-mobile/android-activity/blob/b4ddf059b77be12cdb955d394e65a92e7568d936/README.md), [UIKit bindings](https://docs.rs/objc2-ui-kit/latest/objc2_ui_kit/), [Apple widget extension](https://developer.apple.com/documentation/widgetkit/creating-a-widget-extension), [Apple Live Activities](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities), [objc2 framework tracker](https://github.com/madsmtm/objc2/issues/393).

## 2. Terminal architecture must beat an already specialized baseline

The upstream client audit found that stock T3 already uses libghostty-vt WASM and Canvas2D, a singleton WASM runtime with per-terminal handles, dirty-row rendering, batched backgrounds and equal-style text runs, device-pixel row snapping, and no React state in the render loop. Android shares the C ABI. Recommending “use a native terminal parser” or “batch canvas draws” is therefore not a new improvement over upstream.

The legitimate Rust target is a shared terminal state engine with:

1. Host-owned PTY process lifecycle, correct shell selection/environment, signal handling and resize.
2. Ordered byte transport with bounded queues, sequence/generation tracking and snapshot/replay semantics.
3. Rust parser/grid state on clients; specialized renderers consume dirty cells/rows rather than reconstructing chat or terminal state.
4. Independent input, clipboard, accessibility, link detection and mobile-selection layers.
5. One selected viewer's terminal-query replies forwarded to the process, preserving upstream's duplicate-reply prevention.

Alacritty is a concrete engine candidate because its pinned source isolates PTY/event-loop/thread modules behind non-WASM conditions. Parser, Term, Grid and selection stay available to WASM. The pinned crate is 0.26.1-dev; this support landed in November 2026 and must not be described as a long-established stable browser terminal. Zed's terminal crate uses alacritty_terminal, supporting its usefulness as a reusable native engine. WezTerm's portable-pty provides a separate cross-platform PTY API.

Sources: [Alacritty crate manifest](https://github.com/alacritty/alacritty/blob/791efff6d74c66bee390c259e322626ca93aadb6/alacritty_terminal/Cargo.toml), [WASM module gating](https://github.com/alacritty/alacritty/blob/791efff6d74c66bee390c259e322626ca93aadb6/alacritty_terminal/src/lib.rs), [Zed terminal dependency](https://github.com/zed-industries/zed/blob/f126950f9d3b62666f97437ae5d4ccac2272c4db/crates/terminal/Cargo.toml), [portable-pty](https://docs.rs/portable-pty/latest/portable_pty/), [upstream terminal runtime](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/docs/internals/terminal-runtime.md), [upstream Ghostty integration](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/web/src/terminal/ghostty/README.md).

The baseline obligations include 5,000 lines and 8 MiB retained output, trimming old output and long-line prefixes safely rather than dropping fresh output; limits applied on restore/reconnect; alternate-screen behavior; keyboard navigation and shell shortcuts; selection and copy of retained output; links; IME and bracketed paste; Unicode width/combining behavior; DA/DSR/DECRQM replies; and partial UTF-8/control-sequence boundaries. The browser writer's 65,536 UTF-16-unit chunk limit preserves surrogate pairs and binary mode encodes bytes explicitly. Replacing it with a byte API can remove a conversion only if exactly the same protocol meaning is retained.

A Rust parser throughput win alone does not prove a terminal improvement. Required measures are input-to-visible-result during sustained output, output completion, frame presentation and energy/CPU, with identical replay, scrollback, glyph/escape behavior and window size. Alacritty's own vtebench warns it is insufficient to characterize a terminal generally. No selected primary evidence proves Alacritty beats the current Ghostty pipeline for this workload.

## 3. Git, files and search

### Git

Use the gix library, not its explicitly unstable CLI, for native repository read paths and any mutation whose full semantics have been demonstrated. Reuse repository/object/config caches with invalidation; combine related reads into one domain operation; apply bounded parallelism across independent repositories.

The current pinned feature matrix lists clone, fetch, status, object/ref/index access, commit creation and blob/tree diffing. It does not claim push, rebase, full commit merging, hooks or complete checkout/reset workflows. The detailed status document lists further gaps: signing, workflow orchestration, submodule/rename behavior and some cross-cutting format capabilities. A “replace every git invocation with gix” plan would omit real T3 functionality.

T3 uses worktrees, branch switching, pulls, commit-push-PR workflows, hidden-ref checkpoints and multi-repository rollback. Correctness includes preserving relative task-folder layout, dirty files, attributes/filters, hooks/signing, credential behavior, conflicts, and undoing a partially failed multi-folder filesystem restore. A faster object reader is only one component of this contract.

If an installed Git process remains as a compatibility dependency, label it honestly. It can preserve behavior during a staged Rust application rewrite but does not demonstrate that the missing Rust Git workflow is complete. If the destination excludes invoking Git as well, these missing workflows are an explicit project of their own.

Sources: [gix pinned README](https://github.com/GitoxideLabs/gitoxide/blob/732cc157a1481fe9180fa30d926ad2dcf0a8d5d6/README.md), [detailed crate status](https://github.com/GitoxideLabs/gitoxide/blob/732cc157a1481fe9180fa30d926ad2dcf0a8d5d6/crate-status.md).

### File watching and repository search

Use notify events as invalidation hints, followed by reconciliation against actual filesystem state. Native watcher events can be absent on NFS/WSL mounted paths or overflow under load; polling is a documented fallback and has its own cost/visibility limits. A watcher notification is not an authoritative complete file history. Coalesce work by repository/path, cancel superseded tasks, reconcile after overflow and reconnect, and preserve non-UTF-8 path identities where the platform permits them.

Reuse ripgrep's `ignore`, matcher/searcher and regex building blocks for content search. Its documented speed mechanisms include literal prefilters/SIMD, UTF-8-aware automata, batched ignore matching and parallel traversal. If upstream already invokes ripgrep, embedding those crates does not inherit a new “ripgrep versus grep” multiplier. The prospective advantage is retained configuration/index state, avoiding subprocess/text serialization and cancellation at domain boundaries.

For file/palette fuzzy ranking, nucleo is a realistic Rust library used by Helix. It provides background matching and efficient prefilters, but changes scoring and Unicode treatment compared with other matchers. It must not silently replace T3's established title/content/open-history/time/user-role palette ranking. First port the exact ranking to Rust; use nucleo only for a separately specified fuzzy subproblem whose output is allowed to change.

Sources: [notify pinned documentation](https://github.com/notify-rs/notify/blob/7edda71990a9c7f05c3e5e64cf873e1f0652d858/notify/src/lib.rs), [ripgrep pinned README](https://github.com/BurntSushi/ripgrep/blob/b674410666d5aa3fd66c9d4683791ae811fe4fae/README.md), [nucleo pinned README](https://github.com/helix-editor/nucleo/blob/8c16d47cdfa9607d3e44df5f81c635c6f43c65ee/README.md).

## 4. Markdown, syntax, diffs and text layout

**The current T3 client is already optimized in these areas.** The pinned client audit found ChatMarkdown splitting streamed content into cached completed blocks plus the final growing block, with whole-text fallback where task edits or custom extensions require it. Its timeline uses LegendList virtualization, memoized rows and stable scroll anchors. Its diff pool has 2–6 workers, AST LRU capacity 240, a 30-second idle TTL and a 1,000-character tokenized-line limit. On iOS the native diff renderer already has an ASCII fixed-pitch fast path, TextKit for tabs/Unicode, a thread-local measurer, NSCache with 128 layouts, clipped glyph-range drawing, off-main row preparation and stale-work cancellation. These are existing baseline mechanisms to retain and beat, not missing optimizations attributable to the new Rust design.

The composer also requires ProseMirror-compatible Markdown-source offsets, chips, custom clipboard and undo behavior, plus native marked-text composition, multi-item image paste and accessible chip actions. Scripted HTML replies, MCP Apps, preview content and native WebViews remain browser-host capabilities; replacing the surrounding application with Rust does not permit discarding them.

Pinned upstream evidence: [ChatMarkdown](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/web/src/components/ChatMarkdown.tsx), [timeline](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/web/src/components/chat/MessagesTimeline.tsx), [diff worker pool](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/web/src/components/DiffWorkerPoolProvider.tsx), [iOS diff layout](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/mobile/modules/t3-review-diff/ios/ReviewDiffCodeLayout.swift), [iOS composer](https://github.com/pingdotgg/t3code/blob/28706aceb6fb3babf2cbae0dc0c3edd93b9b6d5f/apps/mobile/modules/t3-composer-editor/ios/T3ComposerEditorView.swift).

Choose a compatibility parser before choosing a benchmark headline. Comrak documents CommonMark 0.31.2 and GFM compatibility, with a broad extension surface. Pulldown-cmark has an allocation-conscious pull-event API, source maps and common GFM extensions. Neither event iteration nor SIMD alone establishes an incremental streaming document parser that can accept arbitrary appended source without reinterpreting old source.

For generated text, maintain the source revision and stable render blocks, reparse the active syntactic region, and invalidate earlier blocks when syntax requires it. Reference links can be defined later; list looseness and unclosed fences can change earlier interpretation. A blanket promise that every previous Markdown block is immutable is false.

A useful counterexample is mdtext's author benchmark: roughly 9.5 ms incremental versus 5.1 s full-prefix reparsing for a 1 MiB generated stream. Its README then explicitly says tight/loose list differentiation and reference links are not implemented because they require lookahead/backtracking. That is a mechanism demonstration with reduced semantics, not an acceptable 500× T3 claim or a drop-in parser recommendation.

For large editable files, Ropey offers inexpensive snapshots/edits and Unicode/UTF-16 indexing. Its README explicitly warns that small texts incur unnecessary kilobyte-chunk allocation and that it is an in-memory structure. Use it for large editable buffers, not automatically for every short chat message. Cache immutable completed messages as compact strings/blocks.

Use imara-diff for line-first diffing, with bounded fine-grained diffing inside changed regions. Its authors explicitly advise against unbounded character diffing of whole large files and against fine-grained work on pure insertion/deletion or very large changes. Preserve patch/hunk semantics required by T3; a different valid edit script can still change user-visible review behavior.

For syntax highlighting, syntect has an optional pure-Rust fancy-regex backend and supports incremental re-highlighting state. Its own current README says that backend is not faster than Oniguruma on its benchmarks. Tree-sitter supplies excellent incremental parsing mechanisms and has Rust bindings, but its core build compiles C. Calling it a pure-Rust dependency is incorrect. If pure-Rust dependencies are mandatory, syntax/theme compatibility and throughput must be verified for the selected Rust backend instead of assuming binding language implies implementation language.

For bespoke native text layout, Parley provides the Rust Fontique/HarfRust/Skrifa/ICU4X stack, including shaping, font fallback, bidi and segmentation. It is a useful component, not a complete editor, compositor, platform IME integration or accessibility solution. Avoid duplicating a toolkit's text engine without a measured reason.

Sources: [Comrak](https://github.com/kivikakk/comrak/blob/4c6462f3dbb46b870cc75d329e30e59ecb8a3883/README.md), [pulldown-cmark](https://github.com/pulldown-cmark/pulldown-cmark/blob/584c92bc4d1d400fca52d9bf6eb27ebd685bcff5/README.md), [parser architecture](https://pulldown-cmark.github.io/pulldown-cmark/dev/index.html), [mdtext limitation and benchmark](https://github.com/kirawi/mdtext/blob/dcf95a5819d01387fc70b23832c6e86129aeae5a/README.md), [Ropey](https://github.com/cessen/ropey/blob/1992665990964e5eee68a42a1aed2bd7abcfda87/README.md), [imara-diff](https://github.com/pascalkuthe/imara-diff/blob/f02e46a737c43c0d9c65a42e5e08046bd10fd739/README.md), [syntect](https://github.com/trishume/syntect/blob/4efbec173db6ea83caaf7a34994cb7e4d038a13e/Readme.md), [Tree-sitter build](https://github.com/tree-sitter/tree-sitter/blob/32594ac6e0532a31bcca7fcd043c34ff5e5e007a/lib/binding_rust/build.rs), [Parley](https://github.com/linebender/parley/blob/cb702f2441be241ede571950e7ba4feb21bcdcb6/README.md).

## 6. What can be claimed before measurements

Algorithmically, avoiding repeated full-prefix parsing can reduce work from a sum of growing prefixes to processing new/invalidated regions, subject to actual language semantics. Avoiding repeated whole-repository scans can reduce work to changed entries plus reconciliation. A viewport bounds painting by visible content rather than the entire history, but upstream already uses virtualization and terminal dirty regions. None of these bounds proves a particular framework or language is faster at equal work.

The decisive candidate design should therefore put the expensive operations in shared Rust modules with explicit input revisions, stable identities, cancellation and output budgets. Measure CPU/allocations/bytes copied and end-to-end interaction latency against the exact stock source, same data, same rendering features, same device and same concurrency. Count text layout, GPU submission/presentation, browser-worker transfers and mobile ABI boundaries.

Required comparison cases include streaming long conversations while composing text; opening and scrolling history; large markdown/code/diff previews; palette search during provider output; terminal input under output flood; reconnect/replay; concurrent worktree/provider activity; app background/resume; mobile CJK composition and screen readers. A startup-size or parser-throughput result alone cannot accept the full application port.

No current source justifies “Rust makes every feature faster.” The evidence supports a concrete implementation direction: remove repeated work and state duplication in a shared core, use native desktop rendering where it helps, keep browser semantics in the browser, and explicitly complete mobile/platform bridges rather than discarding features.

## 7. Targeted UI coverage follow-up: Makepad, Xilem/Masonry, Freya

**Makepad is the first native-mobile candidate and a native-desktop challenger**, alongside the shared Rust core, GPUI desktop candidate and Dioxus semantic-DOM browser proposal. Makepad supplies substantial mobile input/accessibility/browser integration; custom platform adapters should be the remaining work after testing those integrations. None of these three frameworks establishes complete T3 parity or a speedup over stock.

Source inspection pins: Makepad `506ec05105b9adb08d1d21f9879df181b5244ea7` (2026-10-31), Xilem `9a78df878a9269a88325ebd71f3f68c757f0a396` (2026-11-22), Freya `747c22dca8fc031d4a5c7d24fcbf2c5458238a9b` (2026-11-22). These are current-source inspection pins, not release certifications. Supplemental metadata is in `ui-followup-pins.json`.

### Makepad: materially stronger mobile candidate

The inspected source has real Android, iOS and web implementations:

- iOS uses an invisible native UITextView as the keyboard/composition authority, mirrors selection and marked text with UTF-16 offsets, and draws the visible text/caret itself. It handles keyboard frames, physical keyboards and pasteboard. Its UIKit accessibility adapter provides semantic roles, custom actions, line/page reading content and text-input forwarding; the latter is explicitly described as iOS18.1+. This is more than a text-field-only accessibility badge.
- Android includes a substantial BaseInputConnection implementation covering composition, selection, surrounding text, codepoint deletion and batch edits, plus a virtual accessibility-node provider with actions/text-selection conversion. These are Java toolkit bridges, not a wholly Rust implementation of Android services.
- Web has an actual semantic DOM mirror: roles/ARIA relations, static text, buttons and native input/textarea nodes. Those native inputs own browser selection, clipboard, mobile keyboards and composition while the visible UI is GPU drawn. Do not describe current Makepad as wholly invisible to screen readers. Its handwritten JS runtime/bridge also means the dependency graph is not all Rust.

Its WebView implementation is concrete, with backend-dependent behavior:

| Target | Source-backed host | Remaining T3 qualification |
|---|---|---|
| macOS / iOS | WKWebView attached through native layers, clipped parent/child geometry and focus tracking. | Isolated profiles, navigation/security policies, MCP bridging, arbitrary-site media/input, dialogs, downloads and composition with GPU content. |
| Android | android.webkit.WebView with JavaScript and DOM storage enabled, focus/navigation/crash callbacks and native-layer composition. | Four-layer composition budget; API29–33 geometry can lag a frame; older APIs use topmost views. Validate the T3 overlay/keyboard/preview layouts on actual supported devices. |
| Windows | WebView2 composition controller with focus, pointer and navigation integration. | Runtime discovery/packaging, policies and the full browser capability contract. The inspected loader resolves an internal environment-creation entry point, which deserves OS/runtime upgrade qualification. |
| Desktop Linux, plus desktop fallback | Separate Chromium/CEF host process, shared texture rings and input forwarding; CEF explicitly supports macOS, Windows and desktop Linux. | Host must be packaged. Textured widget currently anchors IME at the widget because the host does not report a caret rectangle. Browser popups are redirected into the same embedded view. Do not assume complete native-browser behavior. |
| WebAssembly | GPU UI plus semantic DOM mirror; the native textured browser-host path is a stub on WASM. | Implement the required real iframe/browser sandbox explicitly; do not assume the native WebView widget ports automatically. |

There is also real application evidence: [Robrix v1.0.0-beta.7](https://github.com/project-robius/robrix/releases/tag/v1.0.0-beta.7), published 2026-11-14 at `87385e10680a5b38cf485cc8657a63f8c7174792`, ships desktop installers, Android APKs and an iOS IPA; its official distribution includes TestFlight. This is stronger evidence than demo builds. It remains a beta Matrix client, not a measured T3 replacement or certification of every feature in the newly inspected Makepad main branch.

The current iOS IME source adds runtime fallback methods to `UICompatibilityInputViewController` to work around an iOS27 failure. Treat that as a concrete platform-maintenance issue to qualify, not proof of App Store rejection or inevitable failure. Likewise, native text/accessibility foundations do not establish T3 composer chip/source-offset/undo/multi-image-paste semantics. Validate VoiceOver/TalkBack reading and chip actions, CJK composition across edits, selection/clipboard, browser overlays and terminal input in the first mobile vertical slice.

Makepad does not supply evidence that T3 widgets, Live Activities, share extensions, provider SDK replacements, DPoP/key-store policy or background behavior are finished. Any remaining handwritten first-party Swift/Kotlin/Java/TS feature implementation is still unfinished Rust-port scope. If the user also requires every toolkit dependency to be Rust, Makepad's Java/JS bridges and external browser engines are additional disqualifying or replacement scope; do not hide that distinction.

### Xilem / Masonry: credible architecture, still experimental

Xilem describes itself as an experimental reactive architecture; Masonry supplies a retained widget tree over winit, Vello/wgpu, Parley/Fontique and AccessKit. Current source actually routes AccessKit tree/actions and IME activation/cursor geometry. Android examples are built with cargo-apk and checked in CI for aarch64. Xilem Web is explicitly a prototype DOM backend sharing Xilem Core, not the same native widget renderer compiled for the web.

This can support a Rust-native/DOM architectural split, and its Rust text stack is attractive. However, the inspected evidence does not qualify a full iOS/T3 mobile app, an integrated real-browser preview, or T3 rich-editor/accessibility parity. Do not promote it over Makepad for the immediate mobile proof merely because its foundations are good. Keep it an alternative if the chosen toolkit fails a concrete requirement.

### Freya: desktop candidate, does not close the mobile/browser gap

Current Freya is its own reactive framework, not accurately described as just a Dioxus wrapper. Its official platform documentation labels Android **highly experimental**, web **experimental**, and lists no qualified iOS target. Web compiles with Emscripten and renders Skia into Canvas/WebGL2. A hidden input implements composition/preedit and clipboard text, but an internal accessibility tree and that hidden input do not by themselves establish a full browser screen-reader DOM surface.

Its HTML facility is now `freya-html` over Blitz0.3.0-beta.3, an HTML/CSS renderer. That is not the real JavaScript-capable browser sandbox T3 needs for arbitrary previews and MCP Apps. Skia also keeps C++ in the dependency graph. Freya is useful for native desktop/rich-text experimentation, but its documented platform maturity does not improve the concrete all-feature mobile/web plan.
